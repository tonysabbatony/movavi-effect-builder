# Posterize Time — отдельная частота кадров

Добавьте Posterize Time через общий каталог эффектов. В параметрах слоя есть ползунок и числовое поле **Частота · кадров/с**: от 5 до 30, начальное значение 15. Частота хранится в JSON как `framesPerSecond.DEFAULT`, не связывается с общей силой.

При общей силе 100% применяется выбранная частота. При 0% — исходные кадры без удержания. Между ними результат удержания смешивается с текущим кадром по общей силе. Длительность, скорость клипа и звук не меняются. Частота не может превысить доступные исходные кадры: для исходника 24 fps значение 30 не создаст дополнительные кадры.

Старые пресеты без framesPerSecond при открытии переводятся на отдельную частоту 15 fps, с обычным направлением общей силы. Имя слоя и shaderPath сохраняются. Экспортируйте обновлённую сборку, чтобы сохранить новый параметр.

## Передать разработчику приложения

Пакет `Posterize_Time_Prototype_developer.zip` содержит актуальные .ps/.vs, JSON, мобильный пример и тестовый Metal runner.

1. Заменить оба шейдера в `ISF_METAL/v1/PosterizeTime/`. В uniforms после cadence добавлен float framesPerSecond. Оба файла должны обновляться вместе.
2. Подключить пресет с `effectType: isf` и `shaderPath: v1/PosterizeTime/PosterizeTime`. Внешний мобильный ZIP содержит all_in_one.json и Layers.zip. Копии .ps/.vs в resources нужны для передачи; штатный загрузчик читает код из глобального ISF_METAL.
3. Только cadence связывается с общей силой: MIN=0, MAX=1, DEFAULT=1. framesPerSecond — фиксированный float: MIN=5, MAX=30, DEFAULT=15. При нулевой общей силе эффект можно пропускать.
4. Сохранить исходный граф из трёх PASSES и PERSISTENT-буферы. Размер HoldClock — 2×1; выражения WIDTH/HEIGHT компенсируют коэффициент 0.77 мобильного host.
5. История принадлежит одному клипу/экземпляру. Кадры обрабатываются последовательно; операции одного экземпляра упорядочиваются на GPU. При seek, trim/time-remap, замене исходника и пересоздании эффекта сбрасывать историю.
6. Для произвольного запроса кадра нужен прогрев от начала временного интервала или запрос исходного кадра в квантованное время. Шейдер не может самостоятельно получить пропущенный исходный кадр.

Проход 0 обновляет или удерживает кадр. Проход 1 сохраняет номер интервала и выбранную частоту в byte-packed метаданных RGBA8/BGRA8. Проход 2 смешивает текущий и удерживаемый кадры по cadence. Временная сетка: floor(max(TIME,0)*fps + 0.0001), используется TIME видео. Обратное время определяется через TIMEDELTA<0; смена частоты — по метаданным. Перемотку вперёд внутри одного интервала и замену исходника host должен определять сам.

Для совместимости новый Metal-код поддерживает старый режим при framesPerSecond<5, но редактор при загрузке обновляет старые JSON. Для новых пресетов использовать только новую схему.

## Проверки

```sh
node tests/posterize-time/test-schedule.cjs
xcrun clang++ -std=c++17 -fobjc-arc -Wno-deprecated-declarations tests/posterize-time/metal-oracle.mm -framework Foundation -framework Metal -o /tmp/posterize-oracle
/tmp/posterize-oracle shaders/PosterizeTime
/tmp/posterize-oracle shaders/PosterizeTime fast
node tests/posterize-time/browser.cjs URL OUTPUT_DIRECTORY
python3 prototypes/posterize-time/build-package.py dist/posterize-time
```

Metal: 78 последовательностей, 9282 кадра в каждом режиме компиляции. Проверяются старый режим, независимые 5/15/30 fps, общая сила 0/50/100%, RGBA8/BGRA8, alpha/цвета, 24/29.97/30/60 fps исходника, смена настроек и сбросы. В смешивании допускается округление 1/255. JS отдельно проверяет 10800 решений фиксированной частоты. Browser E2E проверяет редактирование частоты, удержание 5 fps при общей силе 100%, точный обход при 0%, MP4 и сохранение параметра через ZIP.

Это разработка iOS/Metal. Полная мобильная сборка и Android пока не проверялись; интеграция в приложение остаётся обязательной.
