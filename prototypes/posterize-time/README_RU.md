# Posterize Time — прототип для Movavi Effect Builder

## Попробовать на компьютере

Запустите билдер обычным способом и нажмите **Posterize Time · прототип**. Откроются отдельный пресет и синтетическое четырёхсекундное видео. Нажмите Play и меняйте «Общую силу Movavi». Можно загрузить своё видео и экспортировать Before, After или сравнение тем же экспортом видео, что и в v0.12. Файлы остаются на компьютере.

| Общая сила | Обновление изображения |
|---|---:|
| 0% | 5 кадров/с |
| 25% | 10 кадров/с |
| 50% | 15 кадров/с |
| 75% | 20 кадров/с |
| 100% | Каждый исходный кадр без удержания |

Между опорными значениями частота интерполируется. Для 75–100% целевая частота идёт от 20 к 30; ровно при 100% работает обход, включая исходники 60 кадров/с. Частота обновления не может превысить доступные исходные кадры. Например, 20 обновлений/с из 30 исходных кадров дают чередование интервалов; равномернее выглядят делители исходной частоты, например 5, 10 и 15 для 30 кадров/с. Длительность и временная шкала видео не меняются. Шейдер не обрабатывает звук.

## Передать мобильному разработчику

`Posterize_Time_Prototype_developer.zip` содержит Metal `.ps` и `.vs`, JSON, тестовый мобильный пакет, проверочный Metal runner и эту инструкцию. Это прототип **iOS / Metal**; Android не проверялся.

1. Добавить `PosterizeTime.ps` и `PosterizeTime.vs` в ресурсы приложения: `ISF_METAL/v1/PosterizeTime/`.
2. Подключить рецепт из `Posterize_Time_Prototype_mobile.zip`. Внешний ZIP содержит ровно `all_in_one.json` и `Layers.zip`. Ресурс `posterize_time.json` использует `effectType: isf` и `shaderPath: v1/PosterizeTime/PosterizeTime`. Копии шейдеров внутри ресурсов пресета служат для передачи; существующий загрузчик читает код из глобального ISF_METAL, а не из Layers.
3. Не менять `PASSES`, их порядок, `PERSISTENT` или `WIDTH/HEIGHT`. Деление на 0.77 компенсирует коэффициент, применяемый текущим Metal ISF host. HoldClock должен иметь размер **2×1**.
4. Только `cadence` связывается с общей силой: MIN=0, MAX=1. При 0% эффект остаётся активным и даёт 5 кадров/с; host не должен пропускать весь ISF по условию `userIntensity == 0`.
5. История должна принадлежать одному клипу/экземпляру эффекта. Обрабатывать кадры последовательно по времени и последовательно кодировать операции на одной очереди GPU. При конкурентном рендере нескольких кадров одного экземпляра без упорядочивания нужна доработка host.
6. При любом seek, смене исходника, trim/time-remap и пересоздании эффекта сбрасывать persistent-историю. Для произвольного запроса кадра использовать прогрев от начала текущего временного интервала или запрос исходного кадра в квантованное время. Один current-frame shader не может самостоятельно получить пропущенный исходный кадр.

Обратное движение времени/loop определяется через TIMEDELTA<0; смена cadence — по сохранённому параметру. Но перемотку вперёд **внутри того же интервала**, смену исходника с теми же timestamp и потерянные кадры нельзя надёжно определить только из TIME. Браузер сбрасывает историю по событию seeking. Поведение после такого сброса — захват текущего кадра, а не гарантированное восстановление кадра в начале интервала. Для точного совпадения preview/экспорта при произвольном доступе нужен временной фильтр движка, квантующий запрос исходного кадра. Внешнее изменение мобильного приложения здесь не выполнялось.

## Реализация

Проход 0 обновляет или удерживает HoldFrame. Проход 1 записывает в HoldClock номер временного интервала (24 бита) и cadence (16 бит), с флагом валидности. Проход 2 копирует HoldFrame в результат. Используется TIME видео, а не частота вызовов preview и не FRAMEINDEX (в проверенном host FRAMEINDEX не увеличивается). Битовая упаковка сохраняет метаданные в RGBA8/BGRA8; хранить секунды напрямую в 8-битной текстуре нельзя. Визуальный результат не смешивается с исходником по opacity: обновляется весь кадр, включая alpha.

Временная сетка: `floor(max(TIME,0)*fps + 0.0001)`. Номер интервала хранится modulo 16777215. TIME — Float32 движка; прототип рассчитан на обычные короткие видеоклипы, не на многочасовые таймлайны с высокой точностью. 100% — обход удержания при каждом вызове.

## Проверки

```sh
node tests/posterize-time/test-schedule.cjs
xcrun clang++ -std=c++17 -fobjc-arc -Wno-deprecated-declarations tests/posterize-time/metal-oracle.mm -framework Foundation -framework Metal -o /tmp/posterize-oracle
/tmp/posterize-oracle shaders/PosterizeTime
/tmp/posterize-oracle shaders/PosterizeTime fast
python3 prototypes/posterize-time/build-package.py dist/posterize-time
```

Metal runner компилирует поставляемые `.ps/.vs` с тем же удалением повторной структуры, что и ISF parser. Использует три render-прохода, формат RGBA8/BGRA8 и размер metadata 2×1. 42 последовательности / 6042 кадра в каждом режиме fast math: 24, 29.97, 30 и 60 кадров/с; пять опорных положений; пиксели и alpha совпадают с удерживаемым исходником; проверены возврат времени, повторный вызов, смена cadence, размер и независимые экземпляры. JS проверяет 3600 решений по timestamp и сбросы истории.

Browser E2E запускается из полного исходного репозитория билдера: `node tests/posterize-time/browser.cjs URL OUTPUT_DIRECTORY`. Проверены реальное проигрывание, точный обход при 100%, экспорт MP4, декодирование и повторный импорт ZIP. В двух секундах экспортированного сравнения — 60 обновлений Before и 10 After при 0%, без изменения длительности. Старый Glow ×10 также прошёл импорт, редактирование, экспорт и повторный импорт.

Это запуск реального Metal-кода в отдельном runner, **не запуск полной мобильной сборки**. На телефоне ещё нужно проверить preview, перемотку, loop, два клипа подряд, параллельный экспорт, переходы и отсутствие пропуска эффекта при 0%.

Исходники host проверены в локальном checkout multi_superapp: Metal/ISF/ISFBaseEffect.cpp, ISFParser.cpp и Core/ISF/ISFParser.h; KMM ISFPathBuilder.kt и ShaderBuilderImpl.kt. Мобильные исходники не изменялись и не включены в пакет.
